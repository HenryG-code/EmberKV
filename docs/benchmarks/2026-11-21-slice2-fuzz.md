# Slice 2 decoder fuzzing, 21 November 2026

Target `crates/emberkv-storage/fuzz/fuzz_targets/decode.rs`: arbitrary bytes are decoded record after
record, as recovery will read a log. Any panic, any record that does not re-encode to exactly the bytes
it was read from, or memory above libFuzzer's 2 GB limit counts as a failure. Limits: 1 KiB keys,
64 KiB values.

## Reading

- **No crash in 46 million hostile inputs.** The decoder never panicked and everything it accepted was
  canonical, which meets the build plan's "the decoder can never panic or over-allocate" for this run.
- **The fuzzer forged valid header checksums.** Coverage jumped from 64 to 105 edges at about
  3.2 million inputs, when it reached the code after the header check. It learned the checksum bytes
  from the comparisons the decoder makes (the "recommended dictionary" holds them), so the body,
  limit and tombstone paths were exercised, not only the first check.
- **Memory was bounded.** Usage climbed to the allocator's high-water mark and then stayed flat for the
  remaining 42 million inputs. A missing limit check would have let a forged header request gigabytes
  and fail the run with an out-of-memory report.
- **Coverage plateaued**, so a longer run with this target is unlikely to reach new code. New targets
  come with the segment reader (slice 3) and the protocol parser (slice 5).

Fuzzing is not part of CI. A scheduled run that opens an issue on a crash is planned for later.
