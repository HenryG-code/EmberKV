# Slice 0 results on WSL2, 21 November 2026

Feasibility prototype in `prototypes/crash-durability/`. These are development-machine numbers, not
the release benchmark, which runs on native Ubuntu.

## Environment

| Item | Value |
|---|---|
| Machine class | Desktop, Windows 11 with WSL2 Ubuntu |
| Filesystem | ext4 on a WSL2 virtual disk (`/dev/sdf`, from `df -T .`) |
| Build | `cargo build --release` |
| Record | 12-byte header (header CRC-32C, length, body CRC-32C) plus a 1 to 6 digit payload |

## Gate 1: kill loop

First run, `./kill-loop.sh 500`:

```text
runs: 500  passed: 500  failed: 0  acknowledged writes checked: 184019886
```

**This run does not count.** 184 million acknowledged writes in at most 500 x 0.4 seconds is at least
920,000 flushed writes per second, but gate 5 measured 611 per second on ext4. The script created its
working folder with `mktemp -d`, which is under `/tmp`, and on this machine `/tmp` is **tmpfs**, a
filesystem held in memory where a flush does nothing. The test therefore ran on the wrong filesystem.
The format and recovery logic still survived 500 kills, but the gate requires the documented
filesystem.

Fix: the script now works in `crash-runs/` next to itself (ignored by Git) and prints the filesystem
type. Re-run result, `./kill-loop.sh 500`:

```text
Testing on: ext4 filesystem
runs: 500  passed: 500  failed: 0  acknowledged writes checked: 38354
```

38,354 acknowledged writes over 500 runs is about 77 per run. With runs averaging about 0.2 seconds at
611 flushed writes per second, about 120 would be the ceiling; process start-up takes part of each
run. The number is now consistent with gate 5, so this run counts.

**Scope:** a passing kill loop proves that the record format and the checker never lose an acknowledged
write when the **process** is killed. It does not prove that flushing works, because the kernel keeps
unflushed data after a process dies. Removing `sync_all` still passes this test, as expected.

## Gates 2, 3 and the length gate: damaged files

Ten records written by the writer, then damaged with `truncate` and `dd`, then read by the checker:

```text
good:     OK: 10 records, last Some(10), file is clean
torn:     RECOVERED: 9 good records, last Some(9), discarded a torn tail at byte 117
bodyflip: CORRUPT: BadBody at byte 0, refusing to continue          (exit 1)
midflip:  CORRUPT: BadBody at byte 52, refusing to continue         (exit 1)
lenflip:  CORRUPT: BadHeader at byte 0, refusing to continue        (exit 1)
```

- **torn:** the last 2 bytes removed. The 9 complete records before it are kept.
- **bodyflip / midflip:** one bit changed in the first record's payload, and in the fifth record's.
  Damage before the end stops the checker instead of being skipped.
- **lenflip:** one length byte changed from 1 to 255. With a single checksum this was reported as a
  harmless torn tail, which would have discarded every record after it. With the separate header
  checksum it is reported as corruption.

Torn tails produced by real kills mid-write are covered by the kill loop above, where every run
recovered.

## Gate 4: replacing a file

`./replace-loop.sh MODE RUNS` kills a program that replaces a 200,000-line file, at a random moment
between 0 and 149 ms, then checks the file has exactly 200,000 lines from one generation.

```text
Testing on: ext4 filesystem, mode: unsafe
mode: unsafe  runs: 30   broken files: 23
Testing on: ext4 filesystem, mode: safe
mode: safe    runs: 200  broken files: 0
```

- **unsafe** (wipe and rewrite in place): 23 of 30 crashes left a half-written file, and the old
  version was already gone.
- **safe** (write a temporary file, flush, rename, flush the directory): every crash left one complete
  version, old or new.

**Scope:** process crashes only. This proves the write-then-rename order. The two flushes protect against
power loss, which this test cannot observe; that is the later power-loss gate on native Ubuntu.

## Gate 5: cost of flushing every write

| Mode | Records | Time | Records per second |
|---|---|---|---|
| `sync_all` after every write | 2,000 | 3.274 s | 611 |
| No flush | 200,000 | 0.105 s | 1,903,301 |

One run of each so far; repeat each three times to show the spread.

**Reading:**

- Flushing every write is about **3,100 times slower** here: roughly **1.6 ms per flush**, against about
  half a microsecond to append one small record to the kernel's memory.
- At 611 flushed writes per second, a single writer that flushes each write separately is capped by
  the flush, not by Rust, the checksum or the record format. This is the reason for **group commit**
  (later scope, slice 9): several waiting writes share one flush.
- A flush taking milliseconds rather than microseconds suggests WSL2 passes the flush down to the
  physical disk. It is not proof: Microsoft does not document this, so power-loss claims still wait for
  native Ubuntu.

## Gate 6: index memory per key

`index-memory COUNT KEY_LEN KIND`: one million random keys inserted into the in-memory index, each
mapped to a 16-byte `Location { segment: u32, offset: u64, len: u32 }`. Memory is the change in the
process's resident memory (`VmRSS` from `/proc/self/status`). Release build, one run each.

```text
BTreeMap: 1000000 keys of 16 bytes used 91.0 MB  = 95 bytes per key  (raw 32 bytes, 3.0x overhead)
HashMap:  1000000 keys of 16 bytes used 112.5 MB = 118 bytes per key (raw 32 bytes, 3.7x overhead)
BTreeMap: 1000000 keys of 64 bytes used 136.7 MB = 143 bytes per key (raw 80 bytes, 1.8x overhead)
```

**Where the bytes go, for a 16-byte key in a `BTreeMap`:**

| Part | Bytes | Why |
|---|---|---|
| `Vec<u8>` handle stored in the tree | 24 | Pointer, length and capacity |
| `Location` stored in the tree | 16 | The fields, reordered by Rust so there is no padding |
| Spare slots in tree nodes | about 15 to 20 | Nodes hold up to 11 entries and are usually partly full |
| The key's own heap allocation | 32 | 16 bytes of key plus the allocator's bookkeeping, rounded up |
| **Total** | **about 95** | Matches the measurement |

The 64-byte key costs 48 bytes more than the 16-byte key, which is the larger heap allocation (80
instead of 32 bytes) and nothing else. That confirms the breakdown.

`HashMap` used more here because a Rust `HashMap` keeps at least one eighth of its slots empty and
doubles when full: one million entries sit in about two million slots. At other key counts the two can
swap places, so this comparison holds for this count, not in general.

**Design limit, stated:** with 16-byte keys the index costs about **95 bytes per key, roughly 11
million keys per GB of RAM**. Values do not count against this; only keys do. Possible reductions,
later and only with measurements: `Box<[u8]>` instead of `Vec<u8>` (saves the 8-byte capacity field),
storing short keys inline instead of in a separate allocation, or one large buffer for all keys.

The ordered `BTreeMap` is kept: it was not more expensive than `HashMap` at this size, and it allows
range scans (slice 10).

## Gate 7: a failed flush stops all writes

`prototypes/crash-durability/flush-failure`: a `LogWriter` that writes through a `Storage` trait, so tests
can give it a fake disk whose flush fails on a chosen call. `cargo test`:

```text
test tests::a_failed_flush_is_reported_to_the_caller ... ok
test tests::after_a_failed_flush_every_write_is_refused_and_never_retried ... ok
test tests::writes_succeed_while_the_disk_is_healthy ... ok
test result: ok. 3 passed; 0 failed
```

The third test checks that after one failed flush, every later write returns `Stopped`, the flush count
stays at 1 (never retried), and refused writes never reach the disk. This is the rule from research
section 2: on Linux a failed flush can discard the unwritten data, so a retry may falsely succeed.
